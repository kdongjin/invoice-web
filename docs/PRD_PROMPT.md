# PRD 생성용 메타 프롬프트

> 이 문서는 PRD(제품 요구사항 문서) **본문이 아니라**, PRD를 생성하기 위해 Claude(또는 다른 LLM)에게 입력할 **프롬프트 템플릿**입니다.
> 아래 "메타 프롬프트 본문"을 그대로 복사해 Claude Code나 Claude.ai에 붙여넣으면 완성된 PRD 문서가 산출됩니다.

## 사용 방법

1. 아래 "메타 프롬프트 본문" 섹션 전체를 복사한다.
2. `{{ }}` 로 표시된 변수 부분을 실제 값으로 치환한다 (없으면 기본값 그대로 사용 가능).
3. Claude Code에 붙여넣고 실행한다. 필요 시 `sequential-thinking` MCP를 함께 활용하면 단계별 추론 품질이 올라간다.
4. 산출된 PRD는 `docs/PRD.md` 등으로 별도 저장할 것을 권장한다 (이 프롬프트 파일과 혼동하지 않도록).

## 메타 프롬프트 본문

```
당신은 15년 경력의 시니어 프로덕트 매니저이자, Next.js/React 풀스택 아키텍처에 능숙한 테크니컬 PM입니다.
아래 제품 아이디어를 분석하여 개발팀이 바로 스프린트 계획에 착수할 수 있는 수준의 MVP PRD(제품 요구사항 문서)를 작성하세요.

## 1. 제품 아이디어 (Background)

- 제품명(가칭): {{제품명 — 예: 견적서 뷰어 / QuoteView}}
- 한 줄 요약: 관리자가 Notion 데이터베이스에 입력한 견적서 내용을, 별도 로그인 없이 고유 링크를 받은 클라이언트가 웹 페이지에서 확인하고, 필요 시 PDF로 다운로드할 수 있는 서비스.
- 핵심 문제: 현재 견적서는 Notion 페이지를 직접 공유하거나 수동으로 PDF/문서를 제작해 이메일로 전달하고 있어, 브랜딩이 일관되지 않고 매번 수작업이 발생한다.
- 해결 방향: Notion을 "입력 도구(백오피스)"로 그대로 유지하면서, 클라이언트에게 노출되는 화면은 별도의 브랜딩된 웹페이지로 렌더링하고, 그 화면을 그대로 PDF로 변환해 다운로드를 제공한다.

## 2. 이 문서가 기반해야 하는 기술/컨벤션 제약

아래는 실제 이 문서가 구현될 코드베이스(Next.js 16 + shadcn/ui 프로젝트)의 컨벤션이다. PRD의 "기술 아키텍처" 섹션은 반드시 이 제약과 정합성 있게 작성할 것:

- Next.js 16 (App Router, Turbopack 기본, `next lint` 제거 → bare `eslint` 사용)
- `params`/`searchParams`는 비동기(Promise) — 견적서 상세 페이지 라우트(`app/quote/[id]/page.tsx` 등) 설계 시 반영
- 컴포넌트는 4-layer 구조를 따른다: `components/ui`(shadcn 프리미티브, 직접 수정 금지) → `components/patterns`(재사용 조합 부품) → `components/layout`(페이지 골격) → `components/providers`(전역 컨텍스트). 폴더 깊이는 `components/<layer>/<name>.tsx` 2단계 고정.
- shadcn/ui 프리셋: `radix-nova`, baseColor `neutral`, 아이콘은 `lucide-react`
- 다크모드: `next-themes` + class 전략
- 폼/검증이 필요하면 `react-hook-form` + `zod`, 토스트는 `sonner`, 로딩/에러는 Next.js 컨벤션 파일(`loading.tsx`, `error.tsx`)
- 테스트 프레임워크 미설치 상태 — PRD의 "테스트 전략" 섹션에는 이 현실을 반영해 "MVP 단계에서는 수동 QA, 이후 Playwright 등 도입 검토" 식으로 명시할 것
- Notion 연동은 공식 `@notionhq/client` SDK를 전제로 하고, Notion Integration Token 및 대상 Database ID 환경변수 관리 방식을 데이터 모델/보안 섹션에 명시할 것
- PDF 생성 방식은 최소 2개 이상의 후보(예: 브라우저 인쇄 스타일 `@media print` CSS 활용 vs. `@react-pdf/renderer` 혹은 Puppeteer 서버 렌더링)를 비교하고 MVP에 적합한 방식을 권장할 것

## 3. MVP 범위 원칙

- **In Scope**: Notion DB → 웹 렌더링(읽기 전용), 고유 링크 기반 접근(로그인 없음), PDF 다운로드, 최소한의 브랜딩(로고/회사정보 표시)
- **Out of Scope (차기 버전 후보로 명시만)**: 클라이언트 인증/권한 관리, 결제 연동, 견적서 승인/코멘트 기능, 다국어, 여러 관리자 협업, Notion 외 타 데이터소스 지원
- 과도한 설계나 확장성 논의는 피하고, "지금 당장 배포 가능한 최소 단위"를 기준으로 기능을 자르시오.

## 4. 산출물 형식 — 아래 목차를 반드시 이 순서와 제목으로 작성하시오

1. **문서 개요** — 제품명, 작성일, 작성자, 버전, 문서 상태
2. **배경 및 문제 정의** — 현재 워크플로우의 문제점을 구체적 시나리오로 서술
3. **목표 및 성공 지표(KPI)** — 정성적 목표 + 측정 가능한 지표(예: 견적서 발송 후 PDF 다운로드 전환율, 관리자 1건당 소요 시간 단축)
4. **타겟 사용자** — (1) 관리자/견적서 발행자, (2) 클라이언트(견적서 수신자) 두 페르소나를 구분해 니즈 서술
5. **핵심 사용자 시나리오 (User Flow)** — 관리자 플로우와 클라이언트 플로우를 각각 단계별로 서술 (다이어그램 대신 번호 매긴 단계 텍스트로 충분)
6. **기능 요구사항 (In Scope)** — 각 기능에 우선순위(P0/P1/P2)를 매겨 표로 정리
7. **비범위 (Out of Scope)** — 명시적으로 하지 않을 것과 그 이유
8. **기술 아키텍처 개요** — 위 "2. 기술/컨벤션 제약"을 반영해 데이터 흐름도(텍스트 기반)와 라우트 구조 제안
9. **데이터 모델** — Notion Database의 필드(속성)와 웹/PDF에 노출될 항목 간 매핑 테이블
10. **화면 설계 개요** — 견적서 상세 페이지에 필요한 정보 블록(회사정보, 항목 테이블, 합계, 유효기간, PDF 다운로드 버튼 등)을 구조적으로 나열
11. **보안 및 접근 제어** — 고유 링크의 추측 불가능성(UUID 등), Notion API 토큰 보호, 만료 정책 여부
12. **리스크 및 오픈 이슈** — Notion API 레이트리밋, PDF 렌더링 스타일 불일치 등 기술적 리스크를 포함
13. **일정 및 마일스톤** — MVP 개발을 2~3주 내 완료 가능한 단위로 나눈 개략적 일정
14. **부록** — 용어집, 참고 링크

## 5. 작성 지침

- 모든 문서는 한국어로 작성한다. 코드 식별자나 라이브러리명은 원문(영어) 그대로 유지한다.
- 추측이 필요한 부분(예: 정확한 KPI 수치, 일정)은 "가정(Assumption):" 이라고 명시하고 합리적인 기본값을 제시한다.
- 각 기능 요구사항에는 "완료 조건(Acceptance Criteria)"을 최소 1개 이상 붙인다.
- 불필요하게 장황한 설명 대신, 표와 번호 목록을 적극 활용해 개발자가 바로 참고할 수 있게 작성한다.
- 작성 전, 먼저 문제 정의 → 사용자 시나리오 → 기능 범위 → 기술 구조 순으로 사고 과정을 단계별로 정리한 뒤 최종 문서를 산출하시오.
```

## 메타 프롬프트 설계 노트 (참고용)

이 섹션은 프롬프트 자체가 아니라, 위 템플릿을 왜 이렇게 구성했는지에 대한 설명이다.

| 구성 요소 | 목적 |
|-----------|------|
| 역할(Role) 부여 | "시니어 PM + 테크니컬 PM" 페르소나로 기능 나열이 아닌 우선순위/근거 있는 문서를 유도 |
| 기술 제약 섹션 | 이 코드베이스(`CLAUDE.md`, `AGENTS.md`)의 실제 아키텍처와 어긋나는 PRD가 나오는 것을 방지 |
| MVP 범위 원칙 | 범위 크리프(scope creep)를 막고 "지금 배포 가능한 최소 단위"로 강제 수렴 |
| 고정 목차 | 산출물의 일관성을 보장해, 매번 다른 형식의 PRD가 나오는 것을 방지 |
| 작성 지침(가정 명시 등) | LLM이 불확실한 값을 임의로 확정하지 않고 "가정"으로 표시하게 해 리뷰어가 검증 지점을 쉽게 찾도록 함 |

## 향후 확장 아이디어 (이 메타 프롬프트 자체의 개선 방향)

- PRD 산출 후 `code-reviewer` 서브에이전트처럼, PRD 전용 리뷰 체크리스트(완결성/일관성 검증)를 별도 프롬프트로 분리 가능
- Notion API 스펙이 확정되면 "데이터 모델" 섹션에 실제 필드명을 하드코딩한 버전으로 구체화 가능
